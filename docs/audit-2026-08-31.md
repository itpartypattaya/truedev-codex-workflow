# Bergant Workflow audit and Codex-port remediation

Date: 2026-08-31

Audited upstream revision: `9642917d33198e584520f62163b6695093caa3c2` (`v0.2.0`)

Source: `UnBergant/bergant-workflow` and the identical initial revision of this fork

## Scope and evidence

The audit covered both skills, their references, all three hooks, manifests, repository operations,
state handling, dependency behavior, and portability claims. Findings were reproduced by reading the
hook matchers and control flow, constructing representative hook/state inputs, and comparing the
behavior with the current Codex hook and plugin contracts.

Severity convention:

- **P0:** immediate catastrophic or broadly exploitable impact.
- **P1:** high-impact bypass, unsafe repository mutation, or core workflow failure.
- **P2:** material reliability, portability, or maintainability defect.

No P0 issue was confirmed.

## Findings

### P1-1 — Compact enforcement can be bypassed through non-Agent tools

**Evidence:** the only compact matcher is `Agent` in
[`hooks/hooks.json:16`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/hooks/hooks.json#L16).
The hook therefore does not run for Bash, file edits, or MCP mutations. With
`awaitingCompact: true`, a Bash or direct edit invocation proceeds without consulting
`check-compact-gate.sh`.

**Impact:** implementation can continue before the required compact event even though the README
states that the gate forces compaction.

**Remediation:** the Codex `PreToolUse` matcher now covers Bash, `apply_patch`, write aliases,
subagents, and MCP calls. The runner blocks those paths while `awaiting_compact` is true and only a
real compact `SessionStart` clears the flag.

### P1-2 — Hook and state errors fail open

**Evidence:** state reads suppress `jq` errors and compare the empty result to `true`, for example
[`check-compact-gate.sh:21`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/hooks/check-compact-gate.sh#L21)
and
[`check-lifecycle-gate.sh:35-36`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/hooks/check-lifecycle-gate.sh#L35-L36).
Missing `jq`, malformed JSON, or an incompatible state shape results in no block.

**Impact:** the exact conditions in which enforcement is most needed—corruption, dependency drift,
or partial writes—disable it silently.

**Remediation:** the Python runner validates schema version, workflow identity, exact step set,
status order, gate type, approvals, and history shape. If a state file exists but cannot be validated,
matched mutation tools are denied and Stop requests recovery. State is replaced atomically.

### P1-3 — Raw state becomes developer context after compaction

**Evidence:** the compact hook prints the full state with
[`cat "$STATE_FILE"`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/hooks/inject-lifecycle-state.sh#L21).
Task and state strings are not schema-validated or separated from instructions.

**Reproduction:** place instruction-like text in `task` or another string field, then trigger the
compact SessionStart hook. The text is emitted into privileged model context along with the resume
instruction.

**Impact:** a tampered or unexpectedly tracked state file is a prompt-injection surface.

**Remediation:** compact restoration now emits only workflow name, current enum, validated status,
and compact flag. Free-form task, spec, paths, findings, and prompts are excluded and output is capped.

### P1-4 — Git flow can overwrite or commit unrelated user work

**Evidence:** the lifecycle prescribes `git checkout master && git pull && git checkout -b ...`
without a dirty-tree preflight
([`steps.md:9`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/skills/lifecycle/references/steps.md#L9)),
then “commit all changes”
([`steps.md:100`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/skills/lifecycle/references/steps.md#L100)),
and later merges and deletes branches
([`steps.md:123-133`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/skills/lifecycle/references/steps.md#L123-L133)).

**Impact:** repositories using `main`, detached worktrees, dirty user changes, or shared checkouts can
be disrupted; unrelated files may enter the feature commit.

**Remediation:** the runner discovers the real default branch, detects dirty/sensitive paths and
in-progress Git operations, and never mutates Git itself. The skill forbids automatic pull,
stage-all, commit, push, merge, worktree removal, or branch deletion and requires exact authority and
task-owned staging.

### P1-5 — A nominally generic workflow is hardwired to a React/Node toolchain

**Evidence:** lifecycle requires npm, Vitest, and Playwright
([`steps.md:69-84`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/skills/lifecycle/references/steps.md#L69-L84)).
Project initialization defaults to FSD-lite, Biome, Tailwind, shadcn, and Radix
([`phases.md:189-255`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/skills/project-init/references/phases.md#L189-L255)).

**Impact:** Python, PHP, Go, Rust, mobile, backend-only, and established non-React repositories receive
incorrect commands and unnecessary architecture decisions.

**Remediation:** both Codex skills discover commands, frameworks, architecture, and design systems
from repository and user context. UI ceremony is conditional; no technology is selected without a
project-specific reason and current primary-source verification when a version is pinned.

### P2-1 — State paths depend on the session working directory

**Evidence:** every original hook uses a relative `.lifecycle-state.json`, for example
[`check-compact-gate.sh:14`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/hooks/check-compact-gate.sh#L14).

**Impact:** launching the agent in a nested directory can make an active lifecycle appear absent.

**Remediation:** hook input `cwd` is resolved upward to the state directory or Git root. A nested-path
test covers this behavior.

### P2-2 — User-gate enforcement covers lifecycle only and validates no provenance

**Evidence:** only lifecycle has a Stop hook. Project-init relies entirely on prose and a writable
JSON file. Lifecycle checks status ordering but a model can directly mark a gate completed; there is
no `approved_at` requirement or transition ledger.

**Impact:** skipped or fabricated approvals may appear valid after context loss.

**Remediation:** both workflows use the same runner, `awaiting_approval` state, required
`--user-confirmed` transition, approval timestamps, and history. Mutations are blocked while a gate
waits. Approval is still model-mediated; see residual risks.

### P2-3 — Task tracking and slice completion semantics are inconsistent

**Evidence:** the skill requires legacy host task-list calls
([`lifecycle/SKILL.md:38`](https://github.com/UnBergant/bergant-workflow/blob/9642917d33198e584520f62163b6695093caa3c2/skills/lifecycle/SKILL.md#L38))
while its allowed tools do not list those tools. It also says a completed task changes `⏳` to `✅`,
but `⏳` is the slice header status rather than an individual checkbox.

**Impact:** task state can diverge between the host task list, the JSON file, and slice documents.

**Remediation:** Codex's plan is advisory synchronization only; the runner owns workflow state, while
slice status changes only at completed CLOSE. The rewritten slice format uses unambiguous text status.

### P2-4 — No automated regression coverage

**Evidence:** upstream contains no test or CI files for hook decisions, JSON transitions, or recovery.

**Impact:** a prior release already shipped a missing `COMPONENTS` gate, and similar ordering or
fail-open regressions can recur unnoticed.

**Remediation:** the port includes deterministic standard-library tests for malformed state,
transition invariants, compact blocking/clearing, exact approval exemptions, prompt-injection
resistance, nested directories, Git preflight, project-init, and archival.

### P2-5 — Current-version and legal guidance lacks a source-quality contract

**Evidence:** project-init instructs the model to choose the latest versions and perform legal
research, but it does not require primary sources, verification date, jurisdiction, or professional
sign-off.

**Impact:** time-sensitive technical and regulatory claims can be recorded as settled architecture or
requirements without adequate evidence.

**Remediation:** the Codex skill requires current primary/official sources, citations, dates and
jurisdiction for high-stakes claims, while keeping owner/legal sign-offs explicit.

## Verification after remediation

- Python unit/static suite: 16 tests, all passing at final port validation.
- Both skill packages pass the system `skill-creator` quick validator.
- The plugin passes the system `plugin-creator` validator.
- Python files pass `py_compile`.
- JSON manifests and hook configuration are parsed during validation/tests.

## Residual risks and honest boundary

- Codex hooks are guardrails. Hosted or specialized tools may not traverse `PreToolUse`.
- If Python cannot start, Codex reports a hook failure but host policy determines whether the tool
  continues. The skill therefore checks the runner before activating workflow state.
- `--user-confirmed` records that Codex acted after an explicit user message; it is not a
  cryptographic human-attestation mechanism.
- A user or process with filesystem write access can delete state or disable/untrust hooks.
- Protected branches, CI, sandboxing, provider authorization, and human review remain the actual
  security and release boundaries.
- Hook behavior still needs one fresh-session installation smoke test in the Codex app/CLI; unit and
  schema validation do not claim that live host integration passed.
