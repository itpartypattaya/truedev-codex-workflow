# TrueDev Workflow

[English](README.md) | **Русский**

TrueDev Workflow — нативный плагин Codex для длительных продуктовых и инженерных задач. Он
превращает спецификацию в устойчивый набор проектных документов, а затем помогает последовательно
реализовывать вертикальные слайсы с явными контрольными точками для согласования области работ,
проверки, ревью и завершения.

## Что входит в состав

| Компонент | Назначение |
| --- | --- |
| Скилл `project-init` | Спецификация → требования → PRD → архитектура → этапы → вертикальные слайсы → `AGENTS.md` |
| Скилл `lifecycle` | Один слайс: контекст → область работ → план → реализация → доказательства → ревью → документация → завершение |
| Хуки Codex | Блокируют распространённые инструменты изменения при compact-гейтах и ожидании согласования; проверяют состояние при остановке |
| Python-раннер | Кроссплатформенные переходы с проверкой схемы, атомарная запись состояния, архив квитанций и Git-preflight |

Скиллы не привязаны к конкретному стеку. Они определяют команды и соглашения репозитория вместо
предположений о Node.js, React, npm, Vitest, Playwright, Storybook, Tailwind или ветке `master`.

## Требования

- Codex с поддержкой плагинов и хуков
- Git
- Python 3.9 или новее (`python3` в macOS/Linux; `python` в Windows)

Codex проверяет хеши хуков и предлагает доверять им. Если хуки недоступны или отключены, скиллы и
раннер продолжают работать, но автоматическая блокировка изменений отсутствует.

## Установка

Добавьте этот репозиторий как marketplace и установите плагин:

```text
codex plugin marketplace add itpartypattaya/truedev-codex-workflow --ref main
codex plugin add truedev-workflow@truedev-workflow
```

После установки начните новую задачу Codex, чтобы загрузились скиллы и хуки. Откройте `/hooks` в
Codex CLI, проверьте определения хуков и подтвердите доверие к ним.

Для локальной разработки добавьте checkout как корень marketplace:

```text
codex plugin marketplace add <absolute-path-to-this-checkout>
codex plugin add truedev-workflow@truedev-workflow
```

## Использование

```text
$project-init Проанализируй docs/spec.md и подготовь проектную документацию для реализации.
$project-init status

$lifecycle Начни следующий согласованный слайс.
$lifecycle status
$lifecycle Продолжи текущий этап.
```

Согласование происходит в диалоге с Codex. Скилл открывает именованный гейт, показывает
доказательства и останавливается. После явного согласования соответствующего этапа скилл записывает
подтверждение через раннер. Неоднозначное «продолжай» не считается согласованием, если решение
пользователя неясно.

## Устойчивый процесс

```text
спецификация
  → INPUT_VALIDATION → PRD → ARCHITECTURE → PLANNING → DECOMPOSITION → FINALIZE
  → docs/plan/slice-NNN-*.md
  → CONTEXT_CHECK → SCOPE → PLAN → COMPONENTS → IMPLEMENT
  → TEST → VERIFY → REVIEW → DOCUMENT → CLOSE
```

Активное состояние хранится в `.truedev-workflow/` в корне репозитория и игнорируется Git. Раннер
сериализует параллельные переходы, атомарно записывает состояние, отклоняет недопустимые переходы и
архивирует завершённые квитанции в `.truedev-workflow/history/`.

После PLAN lifecycle устанавливает compact-гейт. Реальное сжатие контекста Codex снимает его и
добавляет только разрешённую сводку состояния. Текст задачи и произвольные значения состояния
никогда не повышаются до developer-контекста.

## Границы принудительного контроля

Хуки — полезные защитные ограничения, но не граница безопасности. Pre-tool-хук охватывает команды
оболочки Codex, `apply_patch`, субагентов и вызовы MCP-инструментов, совпавшие с правилами плагина.
Хостинговые инструменты и специализированные пути выполнения могут не отправлять события хуков.
Репозиторные разрешения, sandbox, защищённые ветки, CI и авторизация на стороне провайдера остаются
главными механизмами контроля.

Подробная модель доверия, входные данные хуков, сохраняемые данные и ограничения описаны в
[`SECURITY.md`](SECURITY.md). TrueDev не содержит телеметрии или встроенного сетевого клиента;
полное описание обработки данных приведено в [`PRIVACY.md`](PRIVACY.md).

Если активный файл состояния повреждён, совпавшие вызовы инструментов изменения блокируются.
Явная команда `abandon --user-confirmed` сохраняет исходные байты перед чистым перезапуском.
Корректный lifecycle после смены ветки можно перепривязать только через
`recover --accept-current-branch --user-confirmed`. При отсутствии активного состояния плагин
инертен.

Пока гейт открыт, доказательства читаются через встроенные команды `inspect git-status`,
`inspect git-diff` и `inspect file`. Произвольное чтение через оболочку блокируется, чтобы Git-хелперы
и PowerShell-провайдеры не превращали формально read-only исключение в выполнение кода или чтение за
пределами репозитория. Diff-инспектор пропускает пути с высокой вероятностью наличия учётных данных:
`.env`, приватные ключи, хранилища credentials, каталоги `secrets/` и временное состояние workflow;
обычные исходники вроде `src/secrets.ts` не блокируются. Инспектор перечисляет каждый скрытый путь,
поэтому сокращённый diff нельзя ошибочно принять за полный.

Обе платформы используют общий launcher, который читает `PLUGIN_ROOT` внутри Python и не
предполагает синтаксис Command Prompt `%VAR%`, PowerShell `$env:VAR` или POSIX shell. Launcher требует
абсолютный путь установки: отсутствующее или относительное значение оставляет его инертным, а не
перенаправляет к репозиторию под проверкой и не превращает ошибку запуска в блокировку всех
инструментов репозитория.

## Безопасность Git

Workflow не выполняет автоматически pull, массовый stage, commit, push, создание или слияние PR,
удаление веток или worktree. Перед изменениями репозитория он:

1. определяет настоящую основную и текущую ветки;
2. обнаруживает незакоммиченные изменения, чувствительные или временные пути и незавершённые Git-операции;
3. сохраняет несвязанные пользовательские изменения;
4. требует явного разрешения для внешних или разрушительных действий;
5. при разрешённом коммите добавляет в stage только файлы текущей задачи.

## Разработка

Запуск детерминированного набора тестов:

```text
python -m unittest discover -s tests -v
```

Проверка плагина и обоих скиллов встроенными валидаторами:

```text
python <plugin-creator>/scripts/validate_plugin.py .
python <skill-creator>/scripts/quick_validate.py skills/lifecycle
python <skill-creator>/scripts/quick_validate.py skills/project-init
```

Проверка релизного контракта и создание детерминированного публичного пакета:

```text
python scripts/validate_release.py
python scripts/package_plugin.py
```

ZIP намеренно не содержит marketplace-метаданные, тесты, определения и фикстуры eval, скриншоты и
репозиторную документацию. Публикации только со скиллами не должны объявлять
`interface.screenshots`; изображения для ревью в `docs/images/` остаются отдельными материалами для
подачи и справки.
